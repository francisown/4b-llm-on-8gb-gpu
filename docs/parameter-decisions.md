# 参数决策表：每个值为什么是它

这份表的价值不在数值本身，而在**每个取值都有测量或显存约束作为依据**。面试与文章里能讲的正是这个：被问到"为什么 `max-num-seqs` 用 16 不用 256"时，答案是"因为 256 时 CUDA Graph 捕获不了，实测报错"，而不是"照默认配的"。

三个口径的区分：

- **稳定服务配置**：日常/交付使用的配置（`scripts/start_qwen35_4b_fp8.sh`、离线包）
- **量化公平对照配置**：跑量化三向对比时的配置（编译模式）
- **推测解码公平对照配置**：跑 MTP 扫描时的配置（eager 模式，改动其他变量以隔离 MTP 的影响）

---

## 一、显存与上下文

| 参数 | 稳定服务 | 量化对照 | 推测解码对照 | 为什么是它 | 来源 |
|---|---:|---:|---:|---|---|
| `--max-model-len` | 2048 | 2048 | 1024 | 8 GiB 必须同时留出 16 序列的 KV Cache、CUDA Graph 静态池和 Prefix Cache 的空间。跑到 2048 是当前能稳住的上限；MTP 实验压到 1024 是为了给 MTP 让出预算 | `scripts/*.sh`、`benchmark/results/speculative/README.md` |
| `--max-num-seqs` | 16 | 16 | 4 | **这是本机最关键的一个约束**。Qwen3.5 的 Gated DeltaNet 状态缓存使默认 `max_num_seqs=256` 无法捕获 CUDA Graph；16 是实测能完成捕获的可行值，也足够现有并发实验 | `INT4-AWQ实验记录.md` |
| `--gpu-memory-utilization` | 0.80 | 0.80 | 0.85 | 0.80 留出余量避免 OOM 与波动；spec 实验因为序数只有 4、上下文只有 1024，可以推到 0.85 | 同上 |
| `--max-num-batched-tokens` | 默认 | 默认 | 1024 | 与 1024 上下文对齐，避免单批 token 数超过上下文预算 | `benchmark/results/speculative/README.md` |

## 二、调度与缓存

| 参数 | 取值 | 为什么 | 来源 |
|---|---|---|---|
| `--enable-prefix-caching` | 开 | 多轮对话与共享系统前缀场景下避免重复 prefill。仓库内有冷/热前缀对照实验（`prefix_cache_demo.py`） | `scripts/start_qwen35_4b_fp8.sh` |
| `--enable-chunked-prefill` | 开 | 长 prefill 与持续 decode 混合负载时，避免单个超长 prefill 把已排队请求的 TTFT 顶起来 | `chunked_prefill_demo.py` |
| CUDA Graph | 开（稳定服务/量化对照）<br>关（推测解码对照，用 eager） | 稳定服务要低延迟，编译模式收益明确。spec 扫描改用 eager 是为了隔离 MTP 这一个变量，不让图捕获行为混进对照 | `scripts/*.sh`、spec README |
| `--language-model-only` + `--skip-mm-profiling` | 开 | Qwen3.5-4B 是视觉语言模型，本实验只用文本；跳过多模态 profiling 省启动时间与显存 | `scripts/start_qwen35_4b_fp8.sh` |

## 三、推测解码深度

| 配置 | 接受率 | 结论 |
|---|---:|---|
| 无 MTP（基线） | — | 并发 4 总吞吐 104.26 tok/s |
| MTP-1 | 98.35% | 收益已经很大（并发 4 到 172.47） |
| MTP-2 | 96.66% | 稳步提升 |
| MTP-3 | 96.26% | 稳步提升 |
| **MTP-4（推荐）** | 95.16% | 比 MTP-5 少约 4.6% 的总吞吐，但首 token 与流式间隔更好、推测深度更保守 |
| **MTP-5（吞吐峰值）** | 94.12% | 并发 4 总吞吐 351.37 tok/s，约为基线 3.37 倍 |
| MTP-6 | 90.83% | 开始回落 |
| MTP-8 | 79.40% | TTFT 已超过 1 秒；单用户吞吐只比 MTP-6 快 0.32%，无实际价值 |

**深度选择的判据不是"越深越快"，而是接受率与显存预算的乘积**：接受率随深度单调下降（98.35% → 79.40%），吞吐在 MTP-5 见顶后回落，而 TTFT 在 MTP-6 之后急剧恶化。

**最终决策：日常稳定服务保持无 MTP。**原因是 8 GiB 无法同时容纳正式服务的 2048 上下文、16 序列、CUDA Graph 和 MTP——实测 MTP 叠加 CUDA Graph 后 KV Cache 预算变成 **-1.03 GiB**，直接无法启动。所以：

- 交付包 → 保守的 **N-gram** 配置
- MTP → 只在低并发 + 1024 上下文的性能配置下使用

> **这条是整份表里最值得讲的一个判断**：最优配置和能稳定交付的配置不是同一个东西。很多人会为了峰值数字把服务配到跑不起来的边缘，而正确的做法是把"峰值能力"和"交付配置"明确分成两套，并说清代价。

## 四、环境兼容开关

| 开关 | 取值 | 为什么 | 现行结论 |
|---|---|---|---|
| `VLLM_USE_FLASHINFER_SAMPLER` | 0 | 本机没有完整 CUDA Toolkit，FlashInfer sampler 首次 JIT 找不到 `nvcc` | **仍然成立** |
| `VLLM_USE_V2_MODEL_RUNNER` | 0（历史） | 原以为 WSL2 不支持 V2 runner 所需的 UVA | **已作废**，见下 |
| `VLLM_WSL2_ENABLE_PIN_MEMORY` | 1 | 真正需要的是打开 WSL2 的 pinned memory 开关，而不是退回 V1 runner | 实测 V2 可用，但与 V1 性能等价（并发 1 差 -0.3%，并发 4 差 -0.1%） |

关于最后两行：`INT4-AWQ实验记录.md` 与 `benchmark/results/speculative/README.md` 里那句「WSL 不支持 V2 runner 所需的 UVA」**不准确**。真实情况是 pinned memory 在 WSL2 上受支持但默认关闭。完整证据见 [`wsl2-v2-runner-验证指引.md`](wsl2-v2-runner-验证指引.md)。

**不必因此重跑推测解码扫描**：那次扫描的所有对照组都使用同一个 V1 runner，变量是 MTP 深度而非 runner，所以对照关系有效——错的只是给出的理由。

## 五、这份表里哪些数字可以对外引用

| 类别 | 可否引用 | 说明 |
|---|---|---|
| 参数取值与选择理由 | ✅ 可以 | 不依赖性能测量，是约束推导出来的 |
| 接受率（MTP 各档） | ✅ 可以 | 由模型与算法决定，不随 GPU 时钟漂移 |
| 显存预算结论（如 -1.03 GiB） | ✅ 可以 | 是预算计算，不是吞吐测量 |
| 绝对吞吐数字 | ✅ 可以，但要标口径 | 用根 README 那张「同会话 3 轮均值」表，并注明 n=3 与批内极差。**单次测量的数字不要引用**——本机实测到过单次偏离 3 轮均值 4.3% 的情况 |
| 自制 INT4 相对第三方 FP8 的优势 | ✅ 可以 | +43.0% / +30.0%，两批三次测量方向与量级都稳定 |
| 「自制 FP8 v3 相对第三方 FP8」的吞吐 | ✅ 可以说「等价」 | 两轮独立测量给出一致答案：+1.0% / +0.2%，都在批内极差以内。**不能说"略快"，也不能说"略慢"** |
| 跨批次绝对数值的直接对比 | ❌ 不要 | 第三方 FP8 跨批基本不变，两个自制模型低 6–7%，且已排除热降频、原因未确定 |
