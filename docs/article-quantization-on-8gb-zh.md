# 在 8GB 显存上做 4B 模型量化：一条可复现的取舍链

> 这不是一篇「我跑了多少 tok/s」的文章。我在这个项目里**推翻了自己三个结论**，每一次都是被数据推翻的。那三次推翻比最后的数字有用得多。

**环境**：Windows + WSL2（Ubuntu 22.04）· RTX 5060 8GB · vLLM 0.29.0 · PyTorch 2.13.0+cu130 · CUDA runtime 13.0

---

## 1. 先划清约束

一张消费级 8GB 卡，要跑一个 4B 的视觉语言模型（Qwen3.5-4B），并且要把它做成**别人能自己跑起来的服务**。三个约束决定了后面所有取舍：

1. **显存**。BF16 权重 8.701 GiB，比整张卡还大。原生 vLLM 根本起不来——这不是调参能解决的，必须量化。
2. **KV Cache 和 CUDA Graph 要抢同一块显存**。量化省下来的空间立刻被上下文、并发和静态图吃回去。后面会看到，这直接决定了 `max-num-seqs` 只能是 16。
3. **WSL2 不是原生 Linux**。它带来两个具体的坑（UVA 和 FlashInfer），其中一个后来被我证明是我自己理解错了。

**关于模型选择的说明**：项目里有两个模型，别混——

- **Qwen3.5-4B** 是交付对象：量化、质量评测、推测解码、离线交付包都是它
- **Qwen3-0.6B** 只是引擎的测试负载：要观察"连续批处理如何把并发换成吞吐"，负载本身不能成为瓶颈，而 4B 在 8GB 上到不了高并发

两者的数字**不可互相解释**。这个区分我一开始没写清楚，后来专门修了文档，因为把 0.6B 的吞吐当成交付模型的性能是最容易犯的错。

---

## 2. 量化：两套方案，和一套能自证公平的评测

### 两套量化脚本

**FP8_BLOCK**：权重转 FP8，激活在推理时动态量化。不需要校准文本。

**W4A16 非对称 INT4 + AWQ**：这个复杂得多。

- 校准集用 C-Eval `dev`，固定种子抽 128 条，最大长度 512 tokens
- 方案 W4A16_ASYM，group size 128，AWQ duo scaling，20 个缩放候选
- **逐个 `Qwen3_5DecoderLayer` 校准**，CPU offload
- 200 个线性权重以 packed INT4 保存
- Embedding、视觉模块、`lm_head`、线性注意力中的小型敏感投影**保留 BF16**

体积结果：

| 模型 | 大小 | 相对 BF16 |
|---|---:|---:|
| BF16 | 8.701 GiB | — |
| 第三方 FP8 | 5.281 GiB | -39.3% |
| 自制 FP8 v3 | 5.281 GiB | -39.3% |
| **自制 W4A16 INT4-AWQ** | **3.568 GiB** | **-59.0%** |

### 评测设计：这部分比量化本身更值得看

量化评测最容易作弊的地方是**校准集和评测集重叠**，以及**采样参数不一致**。我这边固定了这些：

- 数据集：C-Eval `val`，**固定 200 题**，覆盖 52 个科目
- 题集冻结并记录样本 SHA-256（`8df8746b…c941`），任何人可以核对是同一批题
- **校准用 `dev`，评测用 `val`，两者不重叠**——避免数据泄漏
- 提示词、题目顺序、答案解析、`temperature=0`、关闭思考、最多 8 个输出 token 全部固定
- 三个量化模型由 vLLM 顺序请求；BF16 因 checkpoint 装不进 8GB，用 Transformers 分层放在 CPU 上、固定 batch size 4 只跑质量基线

最后一条有个必须说明的限制：**BF16 的延迟不能和 GPU 常驻的 vLLM 模型比较**，因为它根本不在同一条件下。我只用它做质量参考。

## 3. 第一个反直觉的发现：总分相同 ≠ 模型等价

结果是这样：

| 模型 | 正确率 | 与 BF16 逐题一致 | 修正 BF16 错题 | 损失 BF16 对题 |
|---|---:|---:|---:|---:|
| BF16 参考 | 141/200（70.5%） | 100.0% | — | — |
| 第三方 FP8 | 141/200（70.5%） | 96.5% | 3 | 3 |
| 自制 FP8 v3 | 141/200（70.5%） | **98.0%** | 2 | 2 |
| 自制 INT4-AWQ v1 | 141/200（70.5%） | **87.0%** | 11 | 11 |

**四个模型的正确率一模一样，都是 141/200。**

如果只看这一行，结论会变成"INT4 量化无损，可以放心用"。这是错的。

看第二列：INT4 与 BF16 的**逐题答案一致率只有 87.0%**，也就是有 **26 道题的选项和 BF16 不同**。它答错了 11 道 BF16 答对的题，同时答对了 11 道 BF16 答错的题——**总分对冲掉了**。

而且 200 道单选题根本不足以证明两个模型等价：141/200 的 Wilson 95% 置信区间大约是 **63.84%–76.39%**，宽得几乎覆盖任何实际差异。

> **结论**：`总分相同` 只能说明"在这 200 题上没观察到准确率差异"。它不能说明模型等价。要把「行为变化」作为独立指标测出来——**逐题一致率**才是那个指标。

这个区分是整份工作里最有用的产出，因为它直接回答"敢不敢在业务里换量化方案"：FP8 你可以放心换（98% 逐题一致），INT4 你得先在自己的数据上单独评测（87%）。

## 4. 踩坑清单

量化过程里踩的坑，按"别人最可能撞上"排序。

### 4.1 Transformers 5.14：`force_accelerate_hooks` 吞掉了 forward 签名

AWQ 校准时报"缺少参数"。追下去发现：Transformers 5.14 的 `force_accelerate_hooks` 装饰器没有保存 `Qwen3_5GatedDeltaNet.forward` 的原始签名，于是 AWQ 把 `hidden_states` 错误地缓存成了嵌套的 `kwargs`，重放时对不上。

修法：**在量化脚本里运行时只恢复签名元数据**，不修改第三方包，也不改 forward 的计算逻辑。这样脚本可移植，升级 transformers 也不会冲突。

**这个坑值得报到上游**——可复现、影响面明确（任何用 AWQ 校准 Qwen3.5 系 Gated DeltaNet 层的人都会撞上）。

### 4.2 `max-num-seqs=256` 捕获不了 CUDA Graph

vLLM 默认 `max_num_seqs=256`。Qwen3.5 的 Gated DeltaNet 状态缓存会因此撑爆显存预算，CUDA Graph 捕获失败。

本机采用 `--max-num-seqs 16`——足够当前的并发实验，且能完成图捕获。**这是这台机器上最关键的一个参数约束**，后面所有性能数字都在这个前提下。

### 4.3 MTP + CUDA Graph 装不下

推测解码用多 token 预测（MTP）时，叠加 CUDA Graph 后 **KV Cache 预算算出来是 -1.03 GiB**——负的，直接起不来。这决定了交付包只能用更保守的 N-gram 配置。

### 4.4 FlashInfer sampler 需要 `nvcc`

vLLM 的 FlashInfer sampler 首次调用会 JIT 编译 CUDA kernel，需要完整的 CUDA Toolkit（我只装了运行时驱动）。因为本实验用 `temperature=0` 贪心解码，不需要融合的 top-k/top-p sampler，所以直接关掉（`VLLM_USE_FLASHINFER_SAMPLER=0`）。

## 5. 第二个发现：我以为的平台限制，其实是个默认关闭的开关

这条我错了很久。

实验记录里我写了：

> WSL 当前不支持 vLLM V2 runner 所需的 UVA

所以一直用 `VLLM_USE_V2_MODEL_RUNNER=0` 退回旧的 V1 runner。**这个结论是错的。**

查上游发现 vLLM 有一个 PR（vllm-project/vllm **#54655**，2026-09-01，"Fall back to the V1 model runner where UVA is unavailable"），**WSL2 就是被报告的那个场景**。而它的说明指出：WSL2 上 pinned memory **是受支持的**，只是被一个开关默认关掉。

看源码注释（`vllm/platforms/cuda.py:302-309`）：

```python
302-                )
303-                return False
304-            # On compatible WSL2 kernels, pinned memory is supported but
305-            # disabled by default. Enable it via VLLM_WSL2_ENABLE_PIN_MEMORY=1.
306-            import vllm.envs as envs
308:            return envs.VLLM_WSL2_ENABLE_PIN_MEMORY
309-        return True
```

实测验证：

| 检查项 | 结果 |
|---|---|
| 内核版本 | 6.18.33.2，远高于门槛 4.19.121 |
| 不带开关 `is_pin_memory_available()` | `False` |
| 带 `VLLM_WSL2_ENABLE_PIN_MEMORY=1` | **`True`** |
| 带开关起服务 | 日志出现 `Using V2 Model Runner` |

**V2 runner 确实能跑。**然后又做了 A/B 性能对照：

| 配置 | 并发 | 输出吞吐 | TTFT P50 | TPOT P50 |
|---|---:|---:|---:|---:|
| A · V1 runner | 1 | 102.35 tok/s | 73.64 ms | 9.26 ms |
| A · V1 runner | 4 | 332.74 tok/s | 252.66 ms | 10.13 ms |
| B · V2 + pinned | 1 | 102.04 tok/s | 74.24 ms | 9.28 ms |
| B · V2 + pinned | 4 | 332.57 tok/s | 252.38 ms | 10.13 ms |

差 **-0.3% / -0.1%**，都在噪声内。

所以真相是第三种，不是我当时设想的任何两种：**V2 可用、可选、但在这个负载上与 V1 没有差别。**

我错的地方不是"选错了 runner"（事实上选哪个都一样），而是**把可用性问题和性能问题混为一谈，并且把一个可配置项描述成了平台限制**。

> **可复用的教训**：遇到"某平台不支持 X"，第一件事是查**它是不是一个默认关闭的开关**。这两者的差别很大——前者意味着"此路不通"，后者意味着"换个配置就好"。

## 6. 第三个发现：我的历史数字复现不出来

这个是意外撞出来的，也是整个项目里最花时间的一段。

### 6.1 差异出现了

在做上面的 A/B 对照时，我顺手看了一眼几天前的记录：**对不上。**

| | 并发 1 | 并发 4 |
|---|---:|---:|
| 2026-09-17 记录 | 109.12 | 359.71 |
| 2026-09-22 复测 | 102.35 | 332.74 |
| 差异 | **-6.2%** | **-7.5%** |

我逐项核对了两次测量的参数：`num_prompts=16`、`max_concurrency=1/4`、`request_rate=inf`、`completed=16`、`failed=0`，输出 token 总数两边都是 2048。**完全一致。**

### 6.2 先证明这不是噪声

第一步是排除"测量不精确"。同一个服务会话内连跑 3 轮：

| | 三个样本 | 均值 | 极差 | 标准差 |
|---|---|---:|---:|---:|
| 并发 1 | 101.48 / 102.70 / 102.49 | 102.22 | 1.2% | 0.66 |
| 并发 4 | 333.35 / 331.47 / 332.07 | 332.29 | 0.6% | 0.96 |

批内极差 0.6%–1.2%，而差异是 6–7%。**所以不能用"噪声大"解释。** 这一步很关键——它堵住了"可能是随机波动"这个借口。

### 6.3 然后记录测量环境，把热降频排除掉

我给压测脚本加了 GPU 状态采样（SM/显存时钟、功耗、功耗墙、温度、pstate、降频原因），每次压测前后各记一次。

结果：

```
throttle_reasons = 0x0000000000000000   ← 无任何降频原因
温度 49–64 °C
功耗 78–105 W（上限 145 W）
SM 时钟全程 2535 → 2752 MHz（不降反升）
```

**"GPU 变热降频导致漂移"这个解释被数据否掉了。**

这一点值得强调：**记录测量环境的价值不一定是给出原因，很多时候是排除假设。** 如果没有这些采样，我很可能会一直在"是不是散热"这个方向上瞎猜。

### 6.4 真正的线索：变化是不均匀的

做完整批重测后，模式出来了：

| 配置 | 并发 1 | 并发 4 |
|---|---:|---:|
| 第三方 FP8 | **+0.7%** | **+2.6%** |
| 自制 FP8 v3 | -7.2% | -5.7% |
| 自制 INT4-AWQ | -5.6% | -7.2% |
| Qwen3-0.6B | -7.6% / -6.1% / +2.2% / -7.3% | |

**第三方 FP8 基本没变，两个自制模型一起低 6–7%。**

如果只是"整台机器慢了一档"，第三方也该跟着掉。所以这不是单一环境因子，而是**与量化内核路径相关**——两个自制模型都走 compressed-tensors + Marlin 这条路径。

**这个原因我到现在也没确定。**候选是不同批次之间内核自动调优/预热状态不同，但我没有验证它，所以不当结论用。

### 6.5 顺手推翻了自己一条相对结论

既然要重测，就把三个量化模型每配置跑 3 轮：

| 模型 | 并发 | 三个样本 | 均值 | 批内极差 |
|---|---:|---|---:|---:|
| 第三方 FP8 | 1 | 71.5 / 72.2 / 72.4 | 72.02 | 1.3% |
| 第三方 FP8 | 4 | 256.6 / 257.0 / 256.9 | 256.83 | 0.1% |
| 自制 FP8 v3 | 1 | 72.8 / 72.7 / 72.7 | 72.76 | 0.1% |
| 自制 FP8 v3 | 4 | 257.1 / 257.5 / 257.4 | 257.33 | 0.1% |
| 自制 INT4 | 1 | 102.9 / 103.0 / 103.0 | 102.99 | 0.1% |
| 自制 INT4 | 4 | 334.1 / 332.9 / 334.7 | 333.90 | 0.6% |

原来我在文档里写过「**自制 FP8 v3 吞吐略高于第三方 FP8**」。现在看：

- 并发 1：72.76 vs 72.02，差 **+1.0%**（批内极差 0.1%）
- 并发 4：257.33 vs 256.83，差 **+0.2%**（批内极差 0.1%）

两轮独立测量给出同样答案：**两者吞吐等价。** 所以那句话删掉了——只能说"等价"，不能说"略快"，也不能说"略慢"。

而 INT4 的优势是稳的：相对第三方 FP8，**并发 1 +43.0%、并发 4 +30.0%**，远大于离散度。

**副产物**：选型结论反而变干净了。原来是"自制 FP8 v3 质量更高、速度也略快"，现在是**纯靠质量**（逐题一致率 98.0% vs 96.5%）。靠一个理由站住的结论，比靠两个含糊理由的结论可靠。

### 6.6 最后一个没想到的：单次测量不可靠，即使同一天

当天早些时候的单次测量里，自制 FP8 v3 并发 4 得到 **246.66**；同一天晚些时候 3 轮均值是 **257.33**。**偏离 4.3%，远超它自己 0.1% 的批内极差。**

另外首批测量普遍略低（第三方 FP8 并发 1 首轮 71.5，后两轮 72.2/72.4），像是预热效应。

> **所以定了一条规矩：对外引用的性能数字，同批次内每配置至少跑 3 轮取均值。**

这条规矩现在写在项目文档里。我最初只对一个配置做过重复测试就认为"单次够用"——是这个 4.3% 的离群点纠正了我。

## 7. 参数是怎么定的

参数值的意义不在数值本身，而在**每个取值都有测量或显存约束作为依据**。挑三个最关键的。

### 7.1 `--max-num-seqs=16`（而不是默认 256）

原因在 4.2 节：Qwen3.5 的 Gated DeltaNet 状态缓存让默认值撑爆预算，CUDA Graph 捕获失败。16 是实测能捕获的可行值。

被问"为什么是这个数"时，答"因为 256 会失败、16 能跑"和答"按默认配的"，是完全不同的两个水平。

### 7.2 推测解码深度：不是越深越快

| 配置 | 接受率 | 并发 4 相对基线 |
|---|---:|---:|
| 无 MTP | — | 1.00× |
| MTP-1 | 98.35% | 1.65× |
| MTP-3 | 96.26% | 2.82× |
| **MTP-4（推荐）** | 95.16% | 3.22× |
| **MTP-5（峰值）** | 94.12% | **3.37×** |
| MTP-6 | 90.83% | 2.95× |
| MTP-8 | 79.40% | 2.59× |

（同一批公平对照内测量，因此比值有效。）

接受率随深度**单调下降**（98.35% → 79.40%），吞吐在 MTP-5 见顶后回落，而 TTFT 在 MTP-6 之后急剧恶化——MTP-8 的 TTFT 超过 1 秒，单用户吞吐只比 MTP-6 快 0.32%，没有实际价值。

**判据不是"越深越快"，而是接受率与显存预算的乘积。**综合 TTFT、吞吐和接受率，实际推荐 MTP-4。

### 7.3 最重要的一条：最优配置 ≠ 可交付配置

MTP 是这套系统里收益最大的单项优化（3.37 倍），但**最终交付包没有启用它**。

原因：8GB 显存无法同时容纳正式服务的 2048 上下文、16 序列、CUDA Graph 和 MTP——叠加后 KV Cache 预算算出来是 **-1.03 GiB**。

所以最后分成两套配置：

- **交付包** → 保守的 N-gram 配置，稳定优先
- **MTP** → 只在低并发 + 1024 上下文的性能配置下使用

> 很多人会为了峰值数字把服务配到跑不起来的边缘。**把"峰值能力"和"交付配置"明确分成两套，并说清各自的代价，这才是工程判断。**

## 8. 引擎基线：批处理是取舍，不是上限

这一节测的是**引擎**，不是模型。用 Qwen3-0.6B 当负载（它够小，能拉到并发 64 而不撞显存）：

| 客户端并发 | 输出吞吐 | TTFT P50 | TPOT P50 | 成功率 |
|---:|---:|---:|---:|---:|
| 1 | 265.76 tok/s | 14.95 ms | 3.67 ms | 100% |
| 4 | 898.85 tok/s | 18.02 ms | 4.32 ms | 100% |
| 16 | 2,811.97 tok/s | 33.84 ms | 5.47 ms | 100% |
| 64 | 5,693.04 tok/s | 94.50 ms | 10.48 ms | 100% |

（单次测量。这一节的结论只依赖趋势，不依赖精确值。）

并发 1 到 64，**总吞吐涨 21.4 倍，但每个请求的 TPOT 涨 2.9 倍、TTFT 涨 6.3 倍。**

**"能接收 64 个并发"和"64 个用户都保持单用户延迟"是两件事。** 容量规划要把这条曲线当成取舍，而不是上限。

## 9. 从"能跑"到"别人能跑"

推理工程的一半工作在服务化和交付上。

**网关**（`FastAPI`，位于客户端与 vLLM 之间）：

- 浏览器聊天页 + 非流式 `POST /chat` + SSE 流式 `POST /chat/stream`（含 TTFT 与端到端延迟）
- 请求 ID 贯穿、Pydantic 校验、Unicode 清理
- 连接/读/写/连接池**四类独立超时**；上游错误转换；客户端断开时取消上游
- 有界并发与队列，超限返回 **HTTP 429 背压**
- `/live`（进程）与 `/health`（上游依赖）分离；`/gateway/status` 观测在途与排队
- Prometheus 计数器、Gauge、延迟直方图；单行 JSON 应用日志
- **9 个不依赖真实模型和 GPU 的 pytest**，覆盖正常、校验失败、上游超时/断连/HTTP 错误、容量拒绝、排队超时
- 非 root Docker 镜像

**离线交付包**：模型、vLLM/PyTorch/CUDA 用户态环境、网关、Compose、一键脚本和 SHA-256 校验打在一起，总大小 **7.49 GiB**，已在全新的 Docker Desktop 环境中完成镜像导入、GPU 检查、模型启动和网页对话验证。

**那 9 个离线测试是我最满意的部分**——它们不需要 GPU、不需要模型、几秒跑完，却覆盖了真实故障路径。这比"在我机器上能跑"有用得多。

## 10. 我从文档里删掉了什么

这部分比前面的成果更能说明问题。

| 被删掉的说法 | 为什么删 |
|---|---|
| 「WSL 不支持 V2 runner 所需的 UVA」 | 实测证明 pinned memory 在 WSL2 上受支持，只是默认关闭。原说法把可配置项当成了平台限制 |
| 「自制 FP8 v3 吞吐略高于第三方 FP8」 | 两轮独立测量显示两者等价（+1.0% / +0.2%，都在批内极差内） |
| 「跨会话漂移最可能是 GPU 时钟/温度状态不同」 | GPU 状态记录显示无任何降频、温度 49–64°C、功耗远低于上限 → 该解释被否掉 |
| 把 Qwen3-0.6B 的吞吐放在项目门面 | 它是测试负载，不是交付模型。用最大的数字当门面是定位错误 |
| 用单次测量的数字写进对外材料 | 实测到单次偏离 3 轮均值 4.3% |

**写下来比说出来重要。** 一份文档里如果只有成功的结论，读的人无法判断作者是真懂还是碰巧做对了。**删掉什么、为什么删，才是判断标准。**

## 11. 如果重做一遍

1. **第一件事就记录测量环境**，而不是等出现无法解释的差异才补。GPU 状态采样成本几乎为零，但它能排除的假设很值钱。
2. **性能数字从第一次测量起就跑 3 轮。** 我为了省 2 分钟，后面花了几个小时搞清楚哪些数字能用。
3. **看到"平台不支持 X"先查开关。** 这一个习惯能省掉一整轮错误的技术决策。
4. **总量相同的指标要配一个"行为一致性"指标。** 准确率会说谎，逐题一致率不会。
5. **把"交付配置"和"峰值配置"从第一天就分开记录**，别等到要交付时才发现最优配置装不下。
